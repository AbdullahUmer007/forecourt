**2026-08-01 · Product name "Forecourt" as a working name.** UK trade term, available-sounding, not yet trade-mark checked. Reversible — flagged to Abdullah as an action.

**2026-08-01 · Stack: TypeScript / Next.js App Router / PostgreSQL with forced RLS / Drizzle / Redis+BullMQ / Cloudflare R2 / Stripe Connect.** One language across app, API and workers for a small team; Postgres RLS is the isolation mechanism; R2 chosen over S3 specifically for zero egress on vehicle photography, which is our dominant bandwidth cost. Reversible early, expensive later.

**2026-08-01 · Shared database, shared schema, `tenant_id` on every row, four isolation layers.** Right trade-off at thousands of tenants with tens of thousands of vehicles each. Schema-per-tenant doesn't scale to thousands of migrations; database-per-tenant is over-engineered. The application never assumes co-location, so a large customer can be moved to a dedicated database later. Reversible with effort.

**2026-08-01 · Money as `bigint` minor units with an explicit currency; no floats anywhere.** Property-tested. Not reversible in practice — everything downstream depends on it.

**2026-08-01 · All regulatory values live in a `compliance_rules` table keyed on the relevant date, never as constants.** UK motor finance regulation moved twice during research (AML threshold to sterling on 30 June 2026; redress scheme partially suspended in July 2026). Changing the law must be a data deployment. Not reversible — it's the whole point.

**2026-08-01 · Chart palette adopted from a validated reference palette rather than derived from the brand hue.** It passes the lightness band, chroma floor, colour-vision-deficiency separation, normal-vision separation and contrast against our exact surfaces (#FFFFFF, #16181D). Deriving a palette from "Petrol" would have needed re-validation with no user benefit. Reversible only by re-running the validator.

**2026-08-01 · Brand primary "Petrol" #0E5A6B rather than a conventional dealer blue.** 7.80:1 on white, distinctive in a category of generic blues, reads premium and mechanical. Reversible — it's a token.

**2026-08-01 · Price ABOVE the direct competitor, not below.** DealersHub is £120+VAT; our Pro tier is £189–£319 stock-banded. Undercutting a one-person operation in a commoditised tier signals a worse product and starts a race we cannot win. We sell the gap, not the price. Reversible, but strategically load-bearing.

**2026-08-01 · Build the free Dealer Site Audit tool BEFORE the CRM.** It generates pipeline before the product exists, proves expertise, doubles as the product demo and becomes our own CI regression suite. Reversible, but it would waste the strongest asset we have.

**2026-08-01 · Never name the competitor in public-facing material; never use their tenure discrepancy as an attack line.** Legally risky, makes us the aggressor, and moves the conversation away from the dealer's own broken pages. Compete instead on the verifiable trust signals they structurally lack. Not reversible without my objection on the record.

**2026-08-01 · Crawler ethics fixed: identified user agent with a contact URL, robots.txt respected, rate-limited to ~1 request/700ms, public pages only, no personal data stored, removal requests honoured immediately.** We are selling compliance; we behave accordingly. Not reversible.

**2026-08-01 · Kennington's real public data used for the demo build, marked "Demo — unsolicited".** Agreed with Abdullah. No contact made, no private data used, public sources only.

**2026-08-01 · `users` is global, not tenant-scoped.** One person may work for two dealers and an external accountant may serve several, so the tenant boundary is the membership rather than the user. `users` gets a membership-scoped RLS policy instead of a `tenant_id`. Reversible with effort; would require rewriting every membership lookup.

**2026-08-01 · `domains.hostname` is globally unique — the one deliberate exception to tenant-scoped uniqueness.** A hostname can only ever resolve to a single tenant, and an unknown or unverified host must 404 rather than fall through to a default. Not reversible: the alternative is a routing ambiguity.

**2026-08-01 · `site_scope` RLS policies are RESTRICTIVE, permanently.** Postgres combines multiple permissive policies with OR, so a permissive `site_scope` returned true whenever `scope_all_sites` was set and OR'd away `tenant_isolation` entirely on every table carrying a `site_id`. This leaked `user_sites` and the whole `audit_events` trail across tenants. Found by the hardened isolation suite. Not reversible — reverting reintroduces a cross-tenant data leak.

**2026-08-01 · The isolation suite asserts SQLSTATE 42501 on rejected cross-tenant INSERTs, and asserts rival data exists before testing against it.** A test that fails on NOT NULL rather than on the policy would pass with RLS switched off; a test with no rival rows passes vacuously. Both were true before this change. Not reversible.

**2026-08-01 · Each tenant is seeded its own copy of the nine system roles rather than sharing platform-level rows.** Lets a dealer rename and adjust roles without affecting anyone else. Costs nine rows per tenant, which is nothing. Reversible.

**2026-08-01 · The compliance profile is enforced in three places** — TypeScript validation for the good error message, database CHECK constraints for the guarantee, and the go-live checklist for operational readiness. Deliberate duplication: the database is the guarantee, the code is the explanation. Reversible but inadvisable.

**2026-08-02 · Vehicle registration is `UNIQUE (tenant_id, registration)`, never global.** A global unique index would let one dealer discover another's stock: enter a registration, get a constraint violation, and you have learned a competitor holds that car. Verified behaviourally — two tenants can both hold WN22HNL, one tenant cannot duplicate it. Note this is the OPPOSITE conclusion to `domains.hostname`, where global uniqueness is the safe choice because a hostname can only resolve to one tenant. Not reversible.

**2026-08-02 · `delivered` is NOT a terminal vehicle state.** A customer has a 30-day short-term right to reject under CRA s.22, so a delivered vehicle can come back. Modelling delivery as terminal would leave no lawful path to record a rejection — the exact scenario the Deal Evidence Ledger exists for. Caught by a reachability test. Reversible only by removing the CRA rejection path, which would be wrong.

**2026-08-02 · Days-to-sell is measured from Live, not from purchase.** Time before Live is `daysToLive` and belongs to the prep team. Blending them blames the sales team for time the car spent in the workshop, and a dealer who spots that stops trusting the whole dashboard. Reversible but inadvisable.

**2026-08-02 · Go-live blockers are returned as a list with per-blocker `overridable` flags, not a boolean.** The dealer needs to see exactly what to fix. An incomplete VAT stock book, a missing price and an unacknowledged mileage anomaly are non-overridable; a missing provenance check is overridable with a recorded reason and a named authoriser. Reversible.

**2026-08-02 · M4 was split into a free half and a paid half, and the free half was built immediately.** DVLA VES and DVSA MOT History are free and self-serve; only valuation (cap hpi) and provenance (HPI Check) need commercial contracts. Labelling the whole module "blocked on contracts" was wrong and would have idled work for weeks. The free half also populates `vehicles.highest_mot_mileage`, which M3's go-live gate already reads — that gate was guarding against data nothing produced. Reversible: the paid adapters slot into the same interface.

**2026-08-02 · Adapters are tested against recorded fixtures, never a live provider.** No contract, no network, no flakiness, and provider behaviour (retries, circuit breaking, partial failure) becomes deterministic. A nightly job should later compare live responses against fixture shape and alert on drift — these APIs change without notice. Reversible.

**2026-08-02 · A combined vehicle lookup returns partial data rather than failing.** If MOT history is down we still return the DVLA record, with the failed source NAMED in a `degraded` array. A buyer standing in an auction hall would rather have half the car than an error. Reversible.

**2026-08-02 · Mileage anomaly detection reports EVERY reading below the running highest, not just the first.** Reporting only the first makes a clocked car look like a single clerical error. Caught by my own test expecting one anomaly where the data honestly contained two. Not reversible without weakening a fraud signal.

**2026-08-02 · EXIF stripping is mandatory and unconditional, enforced by a CHECK constraint.** A phone photo carries GPS. Publishing it discloses where the dealer's stock sits overnight and — for a part-exchange appraisal — usually a customer's home address. `vehicle_media_published_requires_ready` makes it impossible to publish an image that has not been stripped. Not reversible: it is a data-protection control, not an optimisation.

**2026-08-02 · Damage photographs shown to a buyer cannot be deleted, only unpublished.** A photograph of declared condition, shown before sale, is a Consumer Rights Act defence. Enforced by a CHECK constraint as well as in domain logic, and the refusal message offers the lawful alternative rather than just saying no. Not reversible.

**2026-08-02 · Damage photographs sort to the END of the published set.** They must be present and visible — that is the defence — but leading a listing with a scuffed bumper loses the click the defence was meant to protect. Reversible; revisit if dealers ask for it.

**2026-08-02 · `vehicles.published_photo_count` is maintained by a database trigger, not application code.** M3's go-live gate reads it, so a missed update would silently block or unblock a vehicle from being advertised. The database owns anything a gate depends on. Reversible but inadvisable.

**2026-08-02 · Uploads are validated by magic bytes, not the content-type header.** The header is caller-supplied and therefore untrustworthy. HEIC and AVIF are exempted from sniffing because they share an ISO-BMFF container signature; the processor rejects them later if they turn out not to be images. Reversible.

**2026-08-02 · A sold vehicle 301s to the closest-priced car of the same model, never to a "Sold Out" page.** Those pages accumulate as near-identical dead ends, waste crawl budget, compete with each other, and drop a real buyer who clicked through from search onto nothing. Verified by property test that every sold URL resolves to a 301 with a destination. Not reversible.

**2026-08-02 · Facet landing pages always render but only index above a stock threshold.** Two failure modes, both observed on the competitor's estate: pages indexed by Google that 404, and thin pages with no stock. Rendering always (never 404 a URL we minted) with `noindex, follow` below three matching vehicles solves both. Reversible; the threshold is a parameter.

**2026-08-02 · Structured data must never contain a finance figure.** A monthly payment or APR in JSON-LD is still a financial promotion under CONC 3.5.3R, and JSON-LD has nowhere to carry the representative example that must accompany it. `assertNoFinanceFigures` enforces this and is asserted in tests. Not reversible.

**2026-08-02 · `aggregateRating` is omitted unless there is a genuine rating with a non-zero review count.** An invented or zero-count rating is a structured-data violation and can earn a manual penalty. Not reversible.

**2026-08-02 · We audit our own generated output with our own tool, as a blocking test.** We sell by auditing competitors' customers' sites; if ours failed the same checks the pitch collapses, and the first dealer to run the free tool on us would find out. `tests/self-audit/generated-site.test.ts` scores ≥85 today, with the finance check deliberately failing until M8 and asserted as a known gap so it flips when M8 lands. Not reversible.

**2026-08-02 · The public site's markup is generated by template functions, not React components.** The VDP must render completely without JavaScript and ship under 120KB of it. React server components would satisfy that today, but template functions make it impossible to regress: no client bundle to grow, no `use client` to slip in during a refactor, no hydration cost. The Next.js routes are thin wrappers that call the render layer and return the string. Interactivity that genuinely needs JS is added as separately-budgeted progressive enhancement. Reversible, but the zero-JS test would have to be weakened to do it.

**2026-08-02 · An unknown or unverified host returns 404 and never falls through to a default tenant.** Falling through would serve one dealer's stock under another dealer's domain. Unverified matters separately: anyone can point a CNAME at us, and serving before the TXT challenge passes would let them impersonate a dealer on a domain they do not control. Not reversible.

**2026-08-02 · Every cache key carries the tenant, enforced by the `cacheKey` helper's signature.** A cache key without a tenant serves the previous tenant's rendered HTML to the next request — a leak that bypasses the database entirely, where no RLS policy can catch it. Not reversible.

**2026-08-02 · The self-audit now runs against real renderer output rather than a hand-built fixture.** A fixture drifts from the renderer silently; real output cannot. Writing it caught a genuine harness error — I had passed the VDP as the home page, so the `vehicle-page-titles` check failed exactly as designed. The check was right and the test was wrong, which is the correct way round. Not reversible.

**2026-08-02 · The Claude Design VDP was reviewed against our own renderer, and where it was better we changed ours.** It used our tokens exactly, so the comparison was purely about substance. Six things it did better and we have adopted: a real GB plate (yellow field, blue UK band) instead of a flat yellow chip; a labelled "Cash price" with the reduction from our own price history beside it; provenance stated as an outcome rather than a bare badge; declared marks counted and *named*, not just photographed; EV battery health given its typical range for context; and mileage drawn as a chart above the MOT table rather than the table alone. The review was worth more than the design: three of the six are data-model changes, not styling.

**2026-08-02 · We did NOT adopt three things from the design, and each omission is deliberate.** The market guide-price comparison ("priced £651 under guide") needs cap hpi valuations, which are contract-blocked — publishing a comparison we cannot evidence is the exact behaviour we audit competitors for, and there is now a test asserting the page makes no guide-price claim. The advisory-to-prep follow-through ("both tyres replaced in prep on 22 Jul, receipt in the history") needs M14's prep records. The finance block is M8: `financeHtml` stays `null` and no payment figure can appear. The design validated all three as targets; none of them ships on a promise.

**2026-08-02 · Provenance fields are tri-state, and an unknown is never rendered as a clear.** `outstandingFinance`, `stolen` and `writtenOff` are each `true | false | null`. Only an explicit `false` produces "no outstanding finance"; `null` produces silence. Rendering a missing field as good news is how a provenance badge becomes a misrepresentation. Not reversible.

**2026-08-02 · An adverse provenance result is disclosed on the public page, not suppressed.** A vehicle with recorded outstanding finance renders "Provenance — declared" with what was found, and cannot render "Provenance clear". A dealer who wants to hide it is the dealer we are selling against, and it is a Consumer Protection from Unfair Trading Regulations problem as well as a moral one. Not reversible.

**2026-08-02 · The mileage chart's y-axis starts at zero, and no chart is drawn from a single reading.** A truncated axis exaggerates every step on a chart whose entire job is to be trusted, and a one-point "trend" is a lie with a line through it. Both are asserted by test. The MOT table below is the chart's table view, satisfying the design-system rule. Not reversible.

**2026-08-02 · The provenance badge was removed from the trust block and now appears once, above the fold.** It was rendering twice — once as a fact and once as a badge further down. Saying it in two places made neither instance read as a fact. Reversible.

**2026-08-02 · Faceted search is crawl-controlled by an allow-list, not by hope.** Ten facets with five values each is 9.7 million URLs of near-identical content, all competing with each other and with the vehicle pages that actually sell cars. It is the most common way a dealer site quietly destroys its own organic traffic, and it is invisible until it has already happened. Only a small set of shapes may be indexed — all stock, one make, one make plus one model, and any of those plus ONE band-aligned refinement — and every link into anything else carries `rel="nofollow"`. A test enumerates 720 realistic URL combinations and asserts that 26 are indexable. The buyer still gets every filter; only crawlers are constrained. Not reversible without reopening the crawl space.

**2026-08-02 · Only fuel, transmission and body style may refine an indexable URL.** Colour, doors and seats are how a buyer narrows a list once they are already on the site; they are not how anyone arrives from Google. "Used electric BMW" is a search with intent behind it, "used white BMW" is not, and indexing it would add twenty-five thin pages per make. Caught by my own test, which asserted a colour link would be nofollowed when the rule as written would have indexed it — the test was right about the intent and the rule was too permissive. Reversible; the set is a constant.

**2026-08-02 · The canonical URL drops the sort order and keeps the page number.** Sorting reorders a set without changing it, so every sort of one filter combination is duplicate content and canonicalises to the unsorted URL. The page number is kept because canonicalising page 2 to page 1 tells Google page 2 does not exist — a well-known way to lose deep listings. Page 2 and beyond is `noindex, follow`: nothing is orphaned, because every vehicle has its own URL in the sitemap. Not reversible.

**2026-08-02 · Free-form price and mileage ranges are never indexed or followed.** `?price_max=9999` and `?price_max=10000` are two URLs showing almost the same cars, and the space is unbounded. A buyer may still type any number; only the nine declared price bands and six mileage bands are crawlable. Not reversible.

**2026-08-02 · Unknown query parameters are dropped, not passed through.** A marketplace or ad platform appends its own tracking parameters; passing them through would fork the edge cache and mint a new indexable URL per click. `parseSearchQuery` returns the list it ignored so a test can prove nothing silently widened the crawl space. Not reversible.

**2026-08-02 · A zero-count facet option is shown, counted and disabled — never hidden.** A sidebar whose options appear and vanish as you filter is impossible to use, and a buyer cannot tell "there are none of these" from "I have mis-filtered". A selected option stays clickable even at zero, or there is no way to undo it. Reversible.

**2026-08-02 · Monthly-payment search is blocked by an assertion, not merely unbuilt.** It is a large conversion win and it is the single most dangerous facet on the site: a payment figure is a financial promotion under CONC 3.5.3R and the search grid has nowhere to put the representative example. `assertNoPaymentFilter` throws if `monthly`, `ppm`, `payment`, `per_month` or `apr` ever appears in a URL, so adding the facet without `<FinancePromotion>` fails loudly at the boundary instead of shipping a payment nobody signed off. Not reversible before M8 and adviser sign-off.

**2026-08-02 · A zero-result page relaxes the search and shows the closest real cars.** The ladder drops the least important constraint first — colour, then doors and seats, then mileage, then ±10% on budget (roughly a dealer's negotiating room), then gearbox, fuel, model, keyword, and the make last — and stops at the first step with stock. A zero-result page is where a dealer loses a buyer who was ready to spend; an apology is the worst possible thing to put there. Not reversible.

**2026-08-02 · A search that finds nothing is recorded as a demand signal, in an append-only partitioned table.** "Eleven people looked for an automatic Qashqai under £12,000 last month and we had none" is a buying instruction, and it is the reason the zero-result page exists at all. Only thin and empty results are recorded — logging every search would bury the signal and store far more visitor behaviour than we need — and what is stored is the normalised query, never the raw URL, so two spellings of one search aggregate together. Not reversible: a table that can be edited after the fact is not evidence of anything.

**2026-08-02 · The shortlist cookie is set on the first SAVE, never on page load.** That is the entire basis of its PECR "strictly necessary" exemption: it serves a service the user explicitly requested by clicking save. Setting it on arrival would make it a consent-requiring cookie and the exemption would be a fiction. `shouldIssueToken` is a function with a test rather than a comment in a route handler. Not reversible.

**2026-08-02 · A shortlist token is treated as a credential: 32 random bytes, unique per TENANT, never global.** It is a list of what a buyer can afford and when they were looking. Uniqueness is `(tenant_id, token)` rather than `(token)`, because a global unique index would leak the existence of another dealer's token through a conflict — and the isolation suite now asserts both the index shape and that another dealer's token resolves to nothing. A cross-tenant shortlist merge throws rather than returning a wrong answer. Not reversible.

**2026-08-02 · A car that sells stays on the shortlist, marked, with a replacement link.** Deleting it silently makes the buyer think we lost it, and wastes the one moment we know exactly what they wanted. Merging two shortlists keeps the EARLIEST save date, because the CRM shows "saved 11 days ago" and resetting it would misrepresent how long that buyer has been deciding. Reversible.

**2026-08-02 · Saved-search alerts cannot send without an M9 consent record, re-checked at send time.** `canSendAlert` returns false with a stated reason until M9 lands, and thereafter re-tests consent, suppression, whether anything actually matches, and the frequency gap at the moment of sending rather than at the moment of scheduling. A search saved in March and sent in June must be tested against a withdrawal made in May. Not reversible.

**2026-08-02 · The isolation suite's structural gate was exempting every partitioned table.** Gate 1 filtered on `relkind = 'r'`, so a partitioned parent — `search_events` now, `audit_events` and `vehicle_views` later — was never checked for RLS at all. Same blind spot that was found and fixed in `verify-policies.mjs` on 2 August; it had survived in the test. Found by adding the first partitioned table since. Not reversible.

**2026-08-02 · We verify finance quotes; we do not originate them.** `calculations.md` §7 settled this in the planning phase and building M8 confirmed it was right: the finance platform or the lender calculates the payment and the APR and carries the regulatory responsibility for that calculation. What we added is the other half — `verifyQuote` re-derives the amount of credit, the total charge for credit, the total amount payable and the APR itself from the cashflows, and refuses to display anything that does not reconcile. "The provider sent it" is not a defence: the instant we render a figure it is our financial promotion, and the lender's arithmetic error becomes our breach. APR is solved by bisection on the Consumer Credit Directive equation rather than Newton–Raphson, because bisection cannot diverge or land on a spurious root and speed is irrelevant here. Not reversible.

**2026-08-02 · A cost-of-credit figure cannot be rendered without an `ApprovedPromotion`, a type only the gate can construct.** The build plan's acceptance criterion was "there is no code path, in any renderer, that produces a bare payment figure". That is now enforced by the signature: `renderFinancePromotion` takes an `ApprovedPromotion`, and only `approvePromotion()` returns one, and it throws unless the rule is signed off, the example is approved, in date, and arithmetically sound. The vehicle page takes the same token rather than pre-rendered HTML, so it is not possible to hand the page a payment that did not come with its example. The monthly-payment search facet M7 blocked is unlocked by the same proof and nothing else. Not reversible.

**2026-08-02 · The representative example, its field list, its ORDER, its prominence rule and the 51% threshold are versioned data, not code.** CONC 3.5 is being consulted on right now — CP26/15 opened 29 April 2026, closed 17 June 2026, and asks whether the mandatory representative example supports consumer understanding at all and whether 51% is still the right threshold. No policy statement had been published as at 2 August 2026, so the current rules stand, but they may not stand for long. When the FCA moves we ship a signed-off row in `compliance_rules`, not a release. Crucially this also changes what the compliance consultant reviews: a data record with a source URL, rather than a diff. Not reversible.

**2026-08-02 · The seeded compliance rule ships UNSIGNED, and nothing renders until a named person signs it.** `signed_off_by` and `signed_off_at` are null in the migration, `validateRepresentativeExample` fails on an unsigned rule, and an isolation test asserts that no migration ever ships a pre-signed rule. This is the launch gate for M8, M11 and M12, and it is impossible to forget because the feature simply does not work without it. Not reversible.

**2026-08-02 · M1's seeded CONC rule had the representative-example fields in the wrong order, and v1 was left in place anyway.** CONC 3.5.5R prescribes a sequence, and the order is part of the rule rather than a presentation choice; M1's seed also split "rate is fixed" into its own field where the rule treats the rate and its fixed/variable nature as one item. v2 corrects both. v1 was NOT edited or closed — it is the record of what we believed on 1 August, and rewriting history in a compliance table is precisely what that table exists to prevent. The resolver therefore prefers the highest version whose window covers the date, so overlapping open windows are normal and expected. Not reversible.

**2026-08-02 · `compliance_rules` has had no table grant since M1 created it.** `apply_tenant_policies()` issues privileges only to tables carrying a `tenant_id`, and `compliance_rules` deliberately has none — so the application role could never have read the VAT fraction, the AML threshold or the CRA windows it is supposed to read from there. Nothing had exercised it yet. Found by the isolation test written for M8, fixed in `0006_finance.sql` with an explicit grant, plus RLS making it readable by every tenant and writable by none: a tenant able to edit its own representative-example rule could switch its own compliance gate off, which is worse than any single bad promotion.

**2026-08-02 · Cost-of-credit language in free text blocks publishing.** The component gate protects figures the code puts on the page; the realistic breach is a dealer typing "Only £199 a month!" into a description, a caption or a page title, where no component is involved. The scanner is anchored on the credit signal — a period, a rate, an APR, a credit word — and never on the presence of a number, because a scanner that flags every cash price gets switched off within a week and then protects nothing. With a valid example on the page the findings are reported but do not block, because a payment typed into prose cannot follow the lender's rates when they move. Reversible; the patterns are data-shaped.

**2026-08-02 · The representative APR is governed monthly against what actually completed, and a small sample is never reported as a pass.** "Representative" means at least 51% of business resulting from the promotion is expected to be concluded at that rate or better, and the only honest evidence for that expectation is concluded agreements. A drifted representative APR is a live breach on every page of a dealer's website simultaneously and nobody notices until a complaint arrives — which is the exact shape of the problem the industry is currently paying about £9bn for. Below 20 agreements the report says "not a pass, there is simply not enough evidence yet" rather than showing a comfortable percentage. Not reversible.

**2026-08-02 · The payment figure sits above the representative example on the page, never the reverse, and the APR is rendered larger than the payment.** CONC 3.5.6R requires the representative APR to be given greater prominence than any other cost-of-credit figure in the promotion, including the payment that triggered it. That is enforced twice: exactly one item may carry `fp-prominent` and it must be the one the rule names, and a test parses the actual CSS to assert the prominent font size exceeds the payment's. A prominence rule that lives only in someone's intention survives exactly one CSS refactor. Not reversible.

**2026-08-02 · A discretionary commission arrangement cannot be recorded at all.** Banned since January 2021. Modelling it — even to store a historical one — would imply it were an option, and the commission-disclosure validator refuses the type outright. Commission disclosure requires the amount or its basis AND the exact wording version shown, because a disclosure nobody can reproduce is not evidence, which is the finding at the centre of the post-*Hopcraft* liability. Not reversible.

**2026-08-02 · The self-audit gap is closed: our generated site now scores 100 out of 100 on our own tool.** `finance-display` is the heaviest check in the audit at 18 points and was deliberately left failing with a written note that it would start failing the moment M8 landed. It did, and it has been flipped to assert a pass plus a whole-audit score of exactly 100 with no check outstanding. The competitor's live customer site scores 16. That number is now safe to put in front of a dealer.

**2026-08-02 · "Total amount payable" is the statutory figure and excludes the deposit — we had it wrong, and a competitor's page found it.** s.189 CCA 1974 and the Consumer Credit (Disclosure of Information) Regulations 2010 define it as the total amount of credit plus the total charge for credit. We had it as total cash outlay, which reads more naturally in English and is not what the term means. Found by running Kennington's published representative example through `verifyQuote`: every one of their figures reconciled on the statutory definition and failed on ours. Their example is now a permanent regression test. Not reversible.

**2026-08-02 · Kennington's advertised representative APR appears to be their interest rate.** Their published example — £45,999 cash price, £5,999 deposit, £40,000 credit, 48 × £993.50 plus a final £496.75, total charge for credit £8,184.75 — reconciles exactly, but £993.50 is precisely the payment for 8.90% as a NOMINAL annual rate compounded monthly. The APR implied by the same cashflows is 9.8%, and CONC App 1.2 requires the APR to be an effective annual rate. Recorded in `demo/kennington.ts` with the arithmetic. **Not to be used in any customer-facing document until the retained FCA compliance consultant confirms the reading** — being wrong about a competitor's compliance in a pitch would be worse than not raising it.

**2026-08-02 · The demo uses Kennington's real business facts and invented stock.** Their name, address, telephone numbers, opening hours and FRN are public facts about a business we are pitching, and a demo that shows a different dealer's details is a worse demo. Their photographs and listing copy are copyrighted, and a substantial extraction of their 123 listings would also engage the UK sui generis database right — so the stock is invented, shaped to their actual size and price spread, with obviously-generated placeholder photographs. `demo/kennington-stock.json` overrides it if a real scrape is ever taken. Reversible, but the IP position is not.

**2026-08-02 · The public site is route handlers, not page components.** The renderers return complete HTML documents; a React page would nest one document inside another and reintroduce the client bundle the whole design exists to avoid. Next keeps doing what it is good at — routing, caching, revalidation — and nothing stands between a buyer and the markup. As a side effect `apps/site` has no React in its own code at all. Not reversible without weakening the zero-JS test.

**2026-08-02 · Tenant resolution moved out of Next middleware.** Middleware was the right place — it runs before everything, so no handler can forget — but it executes in the Edge runtime, which has no TCP sockets and therefore cannot reach Postgres, where the host-to-tenant mapping lives. The production fix is an edge-readable replica of the domain table; until that exists, `requireTenant` in `src/request.ts` is the ONLY export that hands out a tenant id, so a handler that skips it has nothing to pass to the data layer. `resolveTenant` itself is untouched and still the tested pure function that refuses an unknown or unverified host. **2026-08-03 · Recording a damage mark is deliberately not wired up yet.** The map renders real marks and the interaction is real, but there is no mutation: an INSERT into `appraisal_damage` needs the audit event on every mutation that the definition of done requires, and the M5 media pipeline for the photograph that goes with the mark. A half-written mutation that writes a mark with no audit trail and no photo is worse than an honest read-only view, because it looks finished. Reversible — it is the next slice.

**2026-08-03 · A wrong password and an unknown email give byte-identical answers, and take the same time.** Told apart, they enumerate who has an account here — which for a dealer CRM is a list of that dealership's staff, and across the platform is a list of our customers. The identical message is the easy half; the hard half is that Argon2id deliberately costs ~50ms, so an unknown email that skips it returns in a millisecond and hands the same information to a stopwatch. `burnPasswordTime` verifies against a dummy hash so both paths cost the same. Not reversible.

**2026-08-03 · A session has BOTH an absolute lifetime and an idle timeout, and only the idle one is refreshed by use.** An idle-only timeout never ends for someone who leaves a tab open, which on a shared forecourt machine is most of them. A trusted device gets a longer ABSOLUTE life and the same idle window: trusting a device says "this laptop is ours", not "nobody will walk past it". Not reversible.

**2026-08-03 · Session tokens are stored hashed, and lockout is only cleared by a genuine success.** 32 bytes of CSPRNG output, SHA-256 at rest — not Argon2id, because there is no low-entropy guess to slow down and the hash is computed on every request; what it defends against is a backup, a log line or a support screenshot handing over live sessions. Lockout does not extend while already locked, or anyone can keep a colleague locked out indefinitely by hammering the form, and a failure against an email that does not exist counts against nothing. Not reversible.

**2026-08-03 · MFA is required by what a role CAN DO, not by which role it is.** `requiresMfa(permissions)` means a dealer who grants `finance.commission.read` to a business manager has just made MFA mandatory for that person, with nobody remembering to update a list of role names. A failed sign-in never reports MFA state, because that would confirm the account exists and hint at its privilege level. Not reversible.

**2026-08-03 · The authenticated shell is a route GROUP, not a check each page makes.** Every signed-in route lives under `app/(app)/`, whose layout resolves the session and redirects if there is none — so a new page cannot forget the check, because it is not a call, it is where the file sits. The root layout deliberately reads no session: a root layout that calls `requireSession()` above the sign-in page is a redirect loop, and it is the kind nobody notices until they are actually signed out. `requireSession` redirects rather than throwing, because a signed-out request is an ordinary state and not a 500. Not reversible.

**2026-08-03 · A mutation and its audit event commit in the SAME transaction.** `writeAudit` takes the transaction the mutation is already in rather than opening its own. An audit row committed separately survives a rolled-back change and produces a trail describing something that never happened — which is worse than no trail, because it is believed. There is now a test that rolls a transaction back and asserts NEITHER row survives. Not reversible.

**2026-08-03 · The damage-mark photo is re-encoded, which is what strips the EXIF.** Rule from M5, and the reason is specific: a phone photograph carries GPS, and for a part-exchange appraisal that location is usually a private individual's home address. The pipeline cannot produce an unstripped output because the only path to stored bytes goes through `sharp().rotate().jpeg()` — orientation applied and then discarded, everything else gone because the output is built from pixels. The test builds a JPEG that genuinely contains GPS and asserts the premise before asserting the conclusion; a stripping test whose input was never tagged passes trivially and forever. Not reversible.

**2026-08-03 · An appraisal photo gets its own key shape, sharing the `t/{tenantId}/` prefix.** An appraisal has no vehicle, so `storageKey` does not fit — but `isTenantOwnedKey` only recognises that prefix, and a key shape that quietly bypasses the cross-tenant guard is worse than no guard. Caught by the assertion firing on the first upload against a hand-rolled `tenants/…` path. Not reversible.

**2026-08-03 · A `'use server'` file may export NOTHING but async functions, and neither lint nor tsc says so.** `data/damage.ts` exported one constant alongside the action; Next refuses the whole module at runtime with "can only export async functions, found number". Both static gates passed it. It was found by actually POSTing to the action, which is the argument for driving a mutation end to end rather than trusting that it wires up. The file now carries a note saying why nothing else may be exported from it.

**2026-08-03 · The mark form is handed the server action directly, so it works without JavaScript.** It was originally a client function wrapping the action, which React gives no progressive enhancement — and this form is used on a forecourt on a bad connection. `useActionState` also makes the action reachable by an ordinary POST, which is the only reason the bug above was findable at all. Reversible, but the no-JS behaviour would go with it.

**2026-08-04 · M14: BLOCKED time is reported separately from WORKING time, and overlapping blocks are merged before counting.** This is the module. A dealer's prep problem is almost never that the work is slow — it is that the car sits, waiting for a wing, an approval, a bodyshop slot. "Eleven days in Bodywork" is a number nobody can act on; "eleven days, nine of them waiting for a part" is an instruction. The merge is the load-bearing detail: a car waiting on a part AND an approval simultaneously has sat for one day, not two, and an unmerged total can exceed the time the car has been in stock — at which point nobody believes any of the numbers again, including the right ones. Property-tested three ways: the merged total never exceeds the naive sum, never exceeds the span it covers, and merging twice changes nothing. Not reversible.

**2026-08-04 · The SLA is measured against WORKING time, not wall-clock.** A stage that overran because a supplier had the part on back-order is not the workshop's failure, and flagging it as one teaches everybody to ignore the flag within a fortnight. The waiting time still appears — it is the other half of the weekly report and usually the actionable half — but it is not counted against the person holding the spanner. Not reversible.

**2026-08-04 · The per-cause breakdown deliberately does NOT sum to the blocked total.** One day blocked by both parts and approval contributes one day to `blockedHours` and a full day to each cause. A dealer asking "what is costing me days?" needs to see that approvals contributed too; forcing the causes to sum would mean apportioning a day between two things that were both entirely responsible for it. Documented in the function and asserted by a test, because it looks like a bug to anyone who checks the arithmetic without reading why.

**2026-08-04 · Stage history is its own table, not a `stage_entered_at` column on the card.** A column answers "how long has it been here" and nothing else; AC2 asks for days per vehicle per stage per month against a tenant baseline. Stage events and blocks are content-frozen rather than append-only — each has exactly one lawful update, being closed — the same shape as M12's repair attempts and M13's settlements. Back-dating a stage entry rewrites how long a car sat, which is the number someone is about to make a decision on. Not reversible.

**2026-08-04 · Prep money is NOT duplicated: a task points at a `vehicle_costs` row.** M3 already owns that table and the vehicle's cached `total_cost_pence` already aggregates it. A second source of truth for spend would disagree with the margin panel within a week, and the margin panel is the one a dealer checks. Not reversible.

**2026-08-04 · A card completes only by reaching a stage flagged `is_final`, and one vehicle has at most one open card.** A returned CRA rejection goes through prep again as a SECOND card rather than an edit of the first — otherwise the days metrics silently blend two different pieces of work on the same car. Enforced by a partial unique index, as is "exactly one open stage event per card". Not reversible.

**2026-08-04 · Moving a card is a select and a button, not drag-and-drop.** AC1 asks for one-handed use in a workshop. Dragging a card across a horizontally-scrolling board is a two-handed gesture that needs a flat surface, and it is unusable by keyboard or screen reader without a parallel implementation. Drag can be added on top later as a desk enhancement; it cannot be retrofitted underneath as an accessibility fix. Reversible in presentation, not in the order of work.

**2026-08-04 · An unrecognised MOT advisory is filed as `other`, never guessed into a category.** A tyre job filed under bodywork is worse than one filed as "not sure", because it silently skews the cost analysis the module exists to produce. Advisories are also SUGGESTED, never planned: a pipeline that books work off a government API without asking is one that spends a dealer's money on their behalf. Not reversible.

**2026-08-04 · An unbudgeted prep card reports "unbudgeted", never "0% over".** Treating a missing budget as zero makes every car in the first month look like a disaster, and a report that cries wolf in week one is one nobody opens in week four. Same reasoning as the ten-card floor before any average is reported. Not reversible.

**2026-08-04 · `applyMove` takes a transaction; `moveCard` takes a cookie.** The server action does three things — resolve who is asking, check they may, commit — and everything else lives in a plain module that can be tested against a real database. A function that needs a request cannot be tested without one, and the stage-history invariants are exactly what needs testing. Eleven integration tests now cover the photography gate, the one-open-event invariant, the closed-at-equals-opened-at instant, the audit row, and the override path. Reversible, but the tests would go with it.

**2026-08-04 · `slaState`/`SlaState` collided with `leads.ts` and the barrel silently dropped them — again.** Third occurrence of the same class, and the first one the fixed `pnpm typecheck` actually caught, exactly as the note in `index.ts` predicted. Renamed to `stageSlaState`/`StageSlaState`. Worth recording that the gate paid for itself within one module of being turned on.

**2026-08-04 · Integration tests build their own fixtures; they never read the demo seed.** The first CI run after M14 failed with a foreign-key violation — `tenant_id 11111111-… is not present in table "tenants"` — because CI applies migrations and nothing else, while `mutation-audit` and `prep-move` had been written against the Kennington demo tenant that only exists after `pnpm db:seed && pnpm db:seed:crm`. The tests were gated on `DATABASE_URL` being set, which is not the dependency; the dependency was seeded data. Worse than the failure was its shape: the prep suite guarded each case with `if (!cardId) return`, so on an unseeded database it reported PASS while asserting nothing — the same class as the isolation suite's skipped-but-green run, and caught only because the FK violation happened to be noisy. Fixtures now live in `tests/integration/fixtures.ts` under an `eeeeeeee-…` id space of their own, and an always-on test FAILS when they cannot be built. Not reversible.

**2026-08-04 · The fixture builder takes a Postgres advisory lock.** Vitest runs test files in parallel, so two suites call `ensureFixtures` at the same instant. Against an already-built database every statement is a no-op and nothing collides; against a PRISTINE one they race and one loses on a unique index — so the bug reproduces only on a fresh database, which is to say only in CI. Found by rebuilding a scratch database and running the full suite against it rather than trusting the first green run. `pg_advisory_xact_lock` is transaction-scoped, so it releases on commit or rollback with no cleanup path that can be missed, and the inserts use unqualified `ON CONFLICT DO NOTHING` because naming only `(id)` leaves `users`' unique index on `lower(email)` to raise.

**2026-08-04 · M16: a cost-of-credit figure can never reach a channel feed, and every adapter is built through the guard.** On our own site a payment renders through M8's `ApprovedPromotion` with the representative example beside it. In a feed, a third party renders our payload on *their* page, in *their* layout, and there is nowhere to attach the example CONC 3.5.3R requires — so the answer is not "render it carefully", it is "do not send it". `assertNoFinanceInFeed` runs inside a wrapper every adapter is constructed with, so a channel added next year gets the guard whether or not whoever adds it has read the file. Anchored on the credit signal (a period, a rate, an APR, a credit word) and never on the presence of a number, because a scanner that flags every cash price gets switched off within a week — the same reasoning as M8's language scanner. Not reversible.

**2026-08-04 · The guard protects the PAYLOAD, not the vehicle record, and that is the correct boundary.** A test asserting "every adapter refuses an APR in the headline" failed on CarGurus — which has no headline field, so the text is never sent there and there is nothing to refuse. That is right: the breach is what a portal renders, not what we store. The structural claim is now asserted on the description, which every adapter does carry, and the CarGurus case is its own named test.

**2026-08-04 · M3's go-live gate applies to feeds too.** A car that may not appear on our own site because it has no price, no photographs or no provenance check must not appear on a portal the dealer is paying for. Holding our own shopfront to a higher standard than Auto Trader would be exactly backwards. Not reversible.

**2026-08-04 · Delisting is a DEADLINE stored as a timestamp, not an event someone hopes fired.** A sold car left live generates enquiries the dealer cannot fulfil and is arguably a misleading action under the CPRs. `delist_due_at` is written when the vehicle sells, with a partial index on it, so an overdue takedown is a `WHERE` clause rather than a job nobody checked. The configured delay is honoured — some dealers keep a sold car up for a day to catch "similar vehicle" enquiries — but the default is immediate. Not reversible.

**2026-08-04 · A RESERVED car is not delisted by default.** A reservation falls through often enough that pulling the advert costs the dealer the next buyer. Selling is what ends an advert; `delistOnReserve` exists for dealers who disagree. Reversible — it is a setting.

**2026-08-04 · A rejected payload is never retried automatically; a transport error is.** The portal has already told us the mileage is invalid, and sending identical bytes gets an identical answer while burning the dealer's rate limit. Those are different claims and they get different handling, with the distinction stated in the message a dealer reads. Not reversible.

**2026-08-04 · Feeds deduplicate by payload hash, with keys sorted before hashing.** Without it a nightly rebuild re-pushes every unchanged car to every channel every night — which is how a dealer exhausts their own rate limit with their own stock. Keys are sorted because `JSON.stringify` follows insertion order, the same trap M12's canonical JSON exists to avoid. FNV-1a rather than SHA-256, deliberately: this answers "did anything change?", not "has this been tampered with", and the evidence ledger is where cryptographic strength actually matters.

**2026-08-04 · "Stalled" is a property of a CHANNEL, not of a listing.** The failure that actually happens is a whole feed quietly stopping — nobody notices for three weeks that the forecourt is missing from a portal, because nothing is on fire, there is simply an absence. Several failures and no success in 24 hours is a broken integration; one car failing is a bad record, and conflating them means the alert fires constantly and gets ignored. Reversible; the threshold is a parameter.

**2026-08-04 · M16 was split like M4 was: the mapping half is built, the wire half needs a contract.** Auto Trader partner status has a long lead time, but the canonical model, the eight adapters, validation, preview, publish rules, delisting deadlines, health and retry policy are all buildable and testable now against recorded shapes. Labelling the whole module "blocked on a contract" would have idled it for months, which is the same mistake corrected on 2 August for DVLA and cap hpi.

**2026-08-05 · The MFA gate is enforced on the READ path, in the `(app)` route group, not at session creation.** A session with a correct password and no second factor EXISTS — the user is mid-sign-in — and must not reach a single row. The alternative, a "pending" session in a second table, is a second thing some code path forgets to distinguish from a real one. Every authenticated route is in the group, so the redirect is the whole enforcement and no page has to remember to check. Verified against the running app in all three states: not enrolled → `/mfa`, enrolled but session unsatisfied → `/mfa`, satisfied → 200. Not reversible.

**2026-08-05 · A TOTP secret is written only AFTER a code generated from it verifies.** Enabling MFA on an unverified secret locks the user out of their own account with no way back — and the accounts that mandate MFA are the ones holding commission and evidence-export permissions, which is to say the ones nobody can afford to lose. Until the code checks out, the secret lives in the form and closing the tab costs nothing. Not reversible.

**2026-08-05 · Recovery codes are issued AT enrolment, not offered afterwards.** A code somebody has to remember to generate is one they generate the day after they needed it. Ten codes, Crockford's alphabet so there is no 1/I or 0/O confusion on a printout, hashed on the way in, shown exactly once, and normalised on the way back so a code typed in lower case with the dash missing still works — somebody is reading it off paper, in a hurry, because they have lost their phone. Re-enrolment deletes the old set, or an old printout still opens the account after the phone it replaced was lost. Not reversible.

**2026-08-05 · A recovery code and a reset token are each spent by an UPDATE that only matches an unused row.** The check and the spend are one statement, so two simultaneous submissions cannot both succeed — a read followed by a write would let both through. Tested by firing three concurrent spends and asserting exactly one wins. Not reversible.

**2026-08-05 · Completing a reset revokes every session that user has.** A password reset that leaves the intruder signed in has achieved nothing, and that is the entire reason somebody resets a password. Not reversible.

**2026-08-05 · Rate limiting is PER IP as well as per account, and the two are different defences.** Account lockout counts failures against one account, so one common password sprayed across five hundred accounts trips nothing — each account sees a single failure and nothing looks wrong. That is the attack that actually works against a small business and it is invisible to a per-account counter by construction. An attempt against an account that does not exist still counts towards the address's budget, or enumerating who has an account here is free. Not reversible.

**2026-08-05 · The refusal never says which limit was hit, and never distinguishes rate-limited from wrong.** Telling an attacker "you have hit the address limit" tells them to change address; telling them "that account is locked" confirms the account exists. Every reset-token refusal reads identically too — "already used" versus "expired" tells anyone holding a stolen link which one they are holding. Not reversible.

**2026-08-05 · `auth_attempts` grants the application INSERT and nothing else; the limiter counts through a SECURITY DEFINER function.** A table the app can read row by row is one an injection can enumerate, and this one holds every email anybody has ever tried. `count_auth_attempts` returns two integers and no rows. The three new tables carry no `tenant_id` — deliberately, because credentials belong to a USER and a cross-dealership spray is exactly what a per-tenant table cannot see — so they were added to `verify-policies.mjs`'s SPECIAL list. That file's own comment says "it has no tenant_id is precisely how a table ends up unprotected", which is what would have happened otherwise.

**2026-08-05 · Self-service password reset is NOT built, and the reason is the missing email adapter.** There is no Postmark, no Resend, nothing in `packages/adapters` but the vehicle lookups. A "reset my password" form that silently sends nothing is worse than no form. What exists is the admin-initiated path plus the real token machinery — hashed, single-use, thirty-minute expiry, rate-limited — so when the comms adapter lands the self-service half is a form and a job, not a rewrite.

**2026-08-05 · M17: a margin sale posts NO output VAT on the invoice AND a separate journal for the VAT on the margin. Both halves are mandatory and each is wrong without the other.** Put VAT on the invoice and the sale becomes standard-rated — M11 enforces that at four layers. Omit the journal and the VAT control account never learns about the sale, so the dealer underpays on every margin car they sell and finds out at an inspection, by which point it is years of them. `postingsFor` returns the pair or refuses, so a caller cannot take only the invoice. Not reversible.

**2026-08-05 · A loss-making margin car posts no VAT journal, and that is different from forgetting one.** Each vehicle stands alone under the scheme and a negative margin is never offset against another car's positive one, so there is genuinely nothing owed. Stated as its own test, because "no journal" looks identical to a bug unless the reason is written down.

**2026-08-05 · Nothing posts to an account nobody mapped, and every unmapped account is reported at once.** Not a sensible default, not "Sales" because it sounded right. A wrong account is worse than a missing one: a missing one gets noticed at month end, a wrong one gets reconciled and forgotten. `unmappedAccounts` reports the whole list because a bookkeeper setting up a connection wants to work through it once, not discover them one failed sync at a time. `account_mappings` records who agreed each one and when — "never invent journal entries the accountant did not agree to" is unverifiable without that. **2026-08-05 · A credit note reverses by swapping which side each line is on, never by negating an amount.** A negative debit and a credit look identical in a total and completely different in a ledger. `assertBalanced` refuses any negative outright, and a property test asserts no posting of any size ever produces one. Not reversible.

**2026-08-05 · The dry run is the state a connection starts in, not a mode somebody remembers to pick.** `accounting_connections.live_from` is null until an accountant has read the output and said yes, so the first real post cannot happen by accident. A blocked entry still shows its numbers — the point of a dry run is reading it, and an entry that hides its figures because it is not ready is nothing to approve. Not reversible.

**2026-08-05 · Double entry is enforced by a CHECK constraint as well as by the domain layer.** `posting_balances CHECK (total_debit_pence = total_credit_pence)` — an unbalanced posting should not be storable, let alone sendable. **2026-08-05 · The CSV fallback works with NO mapping at all, falling back to our own account key.** It is the only part of M17 that needs no integration and no contract, and a dealer whose accountant uses something we do not support can hand over a file today. An accountant reading `sales_vehicle_margin` knows what to do with it; a blank column is how a row gets silently dropped on import. **2026-08-05 · The invoice and its margin VAT journal carry DIFFERENT idempotency keys.** Sharing one would make the journal deduplicate against the invoice and silently never post — which is the exact failure the journal exists to prevent, arriving by a different route. Asserted by test.

**2026-08-05 · M18: a deal with no lead is UNATTRIBUTED, never credited to the website.** The single most tempting wrong answer, and it would flatter us specifically — the one table whose entire purpose is being trusted in a negotiation. `Unattributed / walk-in` is a named row rather than an omission, because a dealer whose walk-in trade is a third of their business needs to see that, and excluding it overstates every channel's share of the total. **2026-08-05 · A sale is credited to the lead the deal was actually worked from, and assisting channels are named beside it.** `deals.lead_id` is the closest thing to a fact available. Asserted in both directions. Averages return null below five sales rather than a figure built from two cars — a dealer principal glancing at this on a Monday will act on whatever it says.

**2026-08-05 · The stock list filters through a plain GET form, not a client component.** The filter state lives in the URL, so it is bookmarkable, shareable, survives a refresh, and the back button does what a back button should. It also costs zero JavaScript on the screen staff sit in front of for six hours a day, and it works on the machine in the office running a browser nobody has updated. A React filter bar would have been faster to write and would have made every one of those things worse. Reversible, but there is no reason to.

**2026-08-05 · Cost is redacted in SQL, not in the view.** Where the principal lacks `vehicle.cost.read` the query selects `NULL::bigint` for the cost column, so the number is never in the payload the server rendered from — a hidden field is one `view-source` away, and the field-level rule in the feature skill says the payload must not contain it. The derived gross goes with it under the same rule: a margin is cost wearing a different name. Verified by fetching both screens as each role and grepping what came back. Not reversible.

**2026-08-05 · A car with no recorded cost shows "No cost recorded", never a gross.** `total_cost_pence = 0` on an uncosted car made the whole retail price render as gross — a missing figure dressed as the best possible one, and the same class of lie as reporting an unbudgeted prep card as 0% over. The dealer principal glancing at this list is deciding what to do about a car; a gross that is really an absence is worse than a blank. Not reversible.

**2026-08-05 · The 400ms stock-list budget is a test, and the measured time renders on the page.** `CLAUDE.md` has stated the budget since M1 and nothing enforced it, because there was no list to measure. The suite seeds a thousand real cars and times the query the screen actually runs — through RLS, the site join, the count and both facet queries — because those are what the dealer waits for, not the function in isolation. It asserts the row count first: a performance test against fourteen cars proves nothing and passes forever. Not reversible.

**2026-08-05 · The lead inbox is ordered by who is closest to being lost, not by who arrived last.** A marketplace buyer has enquired on four cars and is waiting for whoever answers first; a fifteen-minute target on a ninety-minute-old Auto Trader lead is more urgent than a sixty-minute target on a five-minute-old walk-in, and newest-first — which is what every CRM ships — buries the first under the second. Unanswered outranks answered unconditionally, then soonest deadline, then arrival. Not reversible.

**2026-08-05 · Every SLA figure renders as a clock time as well as a countdown.** "12 min to respond" is true only at the instant the server rendered it; a tab left open for an hour would go on saying it. "Due 14:32" stays true. The countdown is the useful reading and the clock time is the checkable one, so both are shown. Reversible.

**2026-08-05 · The counts strip is never filtered.** "You have six overdue" is the number a dealer opened the screen for, and it must not change when they filter to one salesperson or one source — a headline that moves with the filter is a headline nobody can act on. The list narrows; the strip does not. Not reversible.

**2026-08-05 · The consent panel answers through `canSend`, and it answers twice per channel.** Re-deriving "may we contact them?" on a screen is how the screen and the sender come to disagree, and the one that is wrong is always the one nobody tested — so the panel calls the same gate the send job calls, which brings expiry, withdrawal, suppression and erasure with it. It asks twice because the two answers genuinely differ: replying to somebody's enquiry is a service message needing no marketing consent, and offering them a different car is marketing that does. A panel showing a single "opted out" flag teaches staff not to answer an enquiry they are perfectly entitled to answer, which is a worse outcome than the one it was trying to prevent. Not reversible.

**2026-08-05 · A `'use client'` module may not import the `@forecourt/domain` barrel, enforced by lint.** The barrel re-exports `evidence.ts`, which imports `node:crypto`, so the build fails outright — the lucky outcome, and how the rule came to be written. The unlucky version of the same mistake is a barrel that happens to bundle: eighty kilobytes of pricing, VAT and commission logic shipped to a phone against a 120KB budget, with nothing failing to say so, and the pricing model readable by any customer who opens dev tools. Domain subpath exports added so a client component can import the one module it needs. Type-only imports are exempt — they are erased. Not reversible.

**2026-08-05 · A postcode is not a postal address.** Using it as the destination for the post channel made the panel state we could write to somebody we have no street address for. A screen answering a question it does not know the answer to is worse than one leaving it blank. Not reversible.

**2026-08-05 · The Consumer Rights Act windows are read from `compliance_rules`, keyed on the delivery date.** Rule 3 says regulatory values are data; this is the read side of that promise for the CRM. Keyed on the relevant date rather than on today, because a deal delivered in March is governed by March's rule and reading today's would silently re-date every historic clock the first time a version is deployed — `compliance_rules` is append-only and versioned precisely so the old answer survives. A missing parameter THROWS rather than defaulting to 30 days: a rule row that does not say what it must say is a deployment problem to be seen, and substituting a plausible number is this system inventing the law. Not reversible.

**2026-08-05 · Each contract-formation option states its consequence beside it.** The field is meaningless to a salesperson as three enum values, and the consequence — whether the customer gets 14 days to change their mind — is the only thing that makes the choice answerable. "Enquired online, signed in the showroom" is the case everybody gets wrong, so it is named on the on-premises option rather than left to be inferred. Reversible in wording, not in intent.

**2026-08-05 · The evidence chain is verified on every read of a deal, and a failure renders above everything it would undermine.** Append-only is a promise about our own code; the hash chain is a property of the data that survives a restore, a migration and an export to a third party — but only if somebody actually checks it. An unverified ledger displayed as though it were sound is worse than no ledger, because it is relied on. The seed hashes its entries through the domain's own `appendEvidence` for the same reason: a demo ledger that merely looks right teaches the wrong thing. Not reversible.

**2026-08-05 · An add-on decision is an appended row, not an update.** `deal_addons` is fully append-only — no UPDATE, no DELETE — and the accept/decline path written against it as an UPDATE could never have run in production. A decision now appends a row carrying the original offer date, and the current position of a product is the latest row for it, which is exactly the shape M9 uses for consent and for the same reason: the history of what was offered and what was decided IS the evidence, and an update destroys half of it. The deal's add-on total is recomputed from the current positions rather than incremented, because an increment drifts the first time something is accepted and then declined. Not reversible.

**2026-08-05 · No cost-of-credit figure appears on the deal screen, and the screen says so.** Rule 5 permits exactly one code path for a monthly payment or an APR, and an internal screen is not an exception to "there is no other code path". The deal shows the amount financed, which is not a cost-of-credit indicator, and states plainly why the monthly payment is absent — otherwise the first assumption is that the CRM is broken. Not reversible.

**2026-08-05 · `pnpm build` is a CI gate.** The CRM had never been production-built and did not build: a page module may export only the reserved names, and neither tsc nor eslint says a word about it. Together with the `'use server'` rule found in M14, that is two framework constraints checked nowhere else — so an app can typecheck, lint and pass 1,500 tests and still be undeployable. Not reversible.

**2026-08-05 · `withSession` and `withTenant` set the database role themselves.** Both doors relied on RLS while connecting as whatever the connection string named — and RLS is not consulted at all for a role with BYPASSRLS, which local development has. The doc comments claimed "the connection uses the app_public role"; that was a statement about how somebody was expected to configure a deployment, and nothing enforced or verified it. Meanwhile almost no loader carries a `tenant_id` predicate of its own, because they were written to rely on the policies. `SET LOCAL ROLE` inside the transaction makes tenant isolation a property of the code rather than of a deployment, and `SET LOCAL` so it ends with the transaction. Not reversible.

**2026-08-05 · The isolation suite now tests the application's doors, not only the policies.** `cross-tenant.test.ts` sets the role itself and then asserts, which proves the policies are correct — and they always were. It could not, by construction, notice that the app never reached them. `app-doors.test.ts` goes through `withSession` and the actual loaders the screens call, while connected as a superuser, which is the worst case. It was verified by removing the fix and watching 8 of its 10 tests fail: a gate that has never been seen to fail is not known to be a gate. Not reversible.

**2026-08-05 · The invoice renderer lives in the product, and the golden-file test points at it.** It was a template defined inside `margin-invoice.test.ts`, which meant the most expensive test in the codebase — showing VAT on a margin invoice standard-rates the whole sale — was guarding a fixture, and whatever the product printed was unguarded. There is now one path from an `Invoice` to something a buyer can read. The test's VAT detector was also blind to `<th scope="col">`, so its negative assertions could not have fired against real markup; it now matches attributes, and that case is in the detector's own tests. Not reversible.

**2026-08-05 · The stock book is content-frozen, not blanket append-only (migration 0019).** M11 declared `make_append_only('stock_book_entries')` while its own column comments said the sale side is "completed at invoice". The trigger refuses every UPDATE, so the sale side could never be written and the twelve mandatory fields could never all be present — the table was unusable for the one thing it exists for. The fix is the treatment `invoices` already has, for the reason that migration itself states: freeze the CONTENT, not the row. Deletion always refused, the purchase side immutable from creation, the sale side writable exactly once. Corrections remain adjusting entries. Not reversible.

**2026-08-05 · The AML threshold version 1 now exists (migration 0020).** M1's note said "Version 1 (EUR) retained for pre-June-2026 records" and it was never inserted, so asking for the threshold in force before 30 June 2026 found no rule at all. The threshold is assessed at the moment cash was RECEIVED, not today, so a payment taken in May 2026 is governed by the May rule — and a system that cannot answer for May either throws or, if somebody later "fixes" it with a fallback, silently applies a threshold that did not exist yet. Its down migration is deliberately a no-op: `compliance_rules` is append-only, and a rollback that could erase a version would make every historic figure unreproducible. Not reversible.

**2026-08-05 · The audit diff stores bigints as strings.** Comparison went through a replacer but the stored value did not, so a bigint survived into the diff and `tx.json` refused it — throwing inside the mutation's own transaction and rolling the whole thing back. Every money mutation would have failed the first time a money field actually changed; invoicing was the first module to do that. Not reversible.

**2026-08-05 · Invoice number gaps are reported as ranges, with a separate count of what is missing.** One stray high number leaves thousands of numbers missing, and the first version of this enumerated every one of them — unreadable on screen and a memory problem in the loader. "sale 2–9000" plus "8,999 missing" says the same thing and can be acted on. Reversible.

**2026-08-05 · A registration is formatted by one function, in the domain.** The CRM's `Reg` component split any seven-character value 4 + 3, which puts a space in the middle of a Northern Ireland plate (ABC 1234 is also seven characters). The invoice document is not a React component and could not have used it anyway, so the rule now lives in `packages/domain` and both call it: current-format plates are spaced, every other UK format is left alone, because a wrong space is worse than none. Not reversible.

**2026-08-05 · What a car is worth does not depend on knowing when it arrived.** Both the stock-value tile and the units-sold count required `booked_in_at`, so a tenant holding £80,347 of stock reported £0 and a delivered car did not count as a unit. Days in stock and days to sell are now nullable all the way through the domain: an undated car is counted in the stock value, EXCLUDED from overage — its age is unknown, and calling it overage would be the report inventing a fact — and named in a caveat saying exactly that. Days-to-sell averages only over the sales where it is known, because treating an unknown as zero drags the average towards a figure nobody's cars achieved. Same rule as M19's completeness score, which never counts an unassessable area as a pass. Not reversible.

**2026-08-05 · The total ROI respects the same sales floor as each row.** The table said "too few sales to state a return" against every channel and then "3.8× overall" in the totals — the report contradicting itself in the space of one screen, and the overall figure is the one a dealer quotes back. Below the floor the total is null too. Not reversible.

**2026-08-05 · Channel names have one implementation, in the domain.** The screen and the CSV each had their own label map, so the file said `website_test_drive` where the screen said "Website test drive". The file is the artefact that ends up on somebody else's desk, which makes it the one that must not look unfinished. Not reversible.

**2026-08-05 · The nav is filtered by the permission its destination enforces.** The page still refuses — UI hiding is a convenience and never the control — but a nav entry leading to a 404 is a worse convenience than none: it tells somebody a feature exists and then implies the product is broken when they click it. Both the VAT book and the Channel P&L call `notFound()` for a principal without the permission, so both were doing exactly that. Reversible.

**2026-08-05 · The Channel P&L's drill-through opens exactly the leads it counted.** The lead inbox gained a received-date filter for this. A drill-through that opens a SUPERSET is worse than none: the reader checks the count against the number they clicked, finds it different, and stops believing the report — which is the one thing this table cannot afford. Not reversible.

**2026-08-05 · Advertising spend is an upsert, and that is the one lawful update in the money layer.** `channel_costs` holds one figure per channel per month by unique index. It is not a record of a transaction; it is the dealer telling us what their invoice said, and they will replace an estimate when the invoice arrives. The `estimated` flag is what keeps that honest — the P&L marks the row rather than presenting a guess as an invoiced amount. Not reversible.

**2026-08-05 · A table, not a chart.** The Channel P&L's artefact is a page a dealer prints or exports and puts on a desk in a negotiation. A bar chart of six channels is decoration beside that, the design system requires a table view next to every chart anyway, and the validated chart palette is a set of hex values that rule 9 keeps out of components. Reversible if a dealer asks for one.

**2026-08-05 · A data breach records its Article 34 risk, in three states (migration 0021).** M19 modelled the Article 33 decision — report to the ICO or record why not — but not the different question Article 34 asks: tell the PEOPLE affected where the risk to them is high. There was no column, so the domain read a field that did not exist and every breach evaluated as low risk, meaning the one statement that says "these people have not been told" could never fire. NULL means nobody has assessed it, which is a finding in itself and is NOT low risk — treating it as low risk is the report deciding the question on the firm's behalf, in the direction that requires no work. Judging a breach not high risk needs a written reason, by CHECK constraint. Not reversible.

**2026-08-05 · Forecourt's own staff have an identity, as a table (migration 0022).** M20's schema referred to an operator as `users(id)` throughout with nothing saying which users work here, so the platform admin application could authenticate nobody. A table rather than a boolean, because staff membership carries a role, a granted/revoked pair with a date, and who granted it — access to every dealer on the platform is not something one person gives themselves, and somebody leaving should be a recorded act rather than a deleted row. Not reversible.

**2026-08-05 · `app_platform` gets column-level grants, not blanket SELECT.** The role has always been BYPASSRLS and had NO GRANTS AT ALL, so it existed as an intention. Granting it blanket read would have been the easy thing: it can see every dealership at once, so what it may read is the only boundary left. The admin application must be able to say how many cars a dealer has and never what their customers are called — so `GRANT SELECT (id, tenant_id, state) ON vehicles`, and no grant at all on contacts, leads, deals, messages, invoices, payments or deal_evidence. Verified: the database refuses `vehicles.registration`. Support that genuinely needs those goes through impersonation, which the dealer grants and which is logged. Not reversible.

**2026-08-05 · The admin app's door is called `acrossTenants`.** The CRM has four isolation layers; this application legitimately has one, because a tenant directory that could only see one tenant would not be a directory. Naming the function for what it does means a reader of any call site can see that this is the code stepping over the boundary the rest of the product spends four layers defending. Not reversible.

**2026-08-05 · `pnpm typecheck` runs both TypeScript programs.** The root tsconfig included `apps/crm` and not `apps/admin`, and `@/*` mapped to the CRM's `src` — so every file in the new app was unchecked, and its `@/data/db` imports would have resolved to the CRM's. Typecheck was passing vacuously, which is the same class of problem as a test that skips and reports green. Two apps cannot share one `@/*` mapping, so they are two programs. Not reversible.

**2026-08-05 · Refunds are not posted to the ledger, and are counted on the screen.** `paymentPostings` models a receipt: debit bank, credit debtors. Reversing the entries is probably the right treatment, and "probably" is not good enough for somebody else's books, so refunds wait for a bookkeeper to confirm it and are named on the screen rather than silently dropped.
